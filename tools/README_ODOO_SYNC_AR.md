# ربط ركاز بجميع الأقسام مع إبقاء الواجهة

هذا الكود يعمل على جهاز/سيرفر ركاز ويقرأ قاعدة SQLite الفعلية دون تعديلها.
واجهة ركاز وصلاحياتها وحساباتها وحساباتها المالية تبقى مصدر التشغيل.
المزامنة باتجاه واحد: ركاز إلى نماذج بيانات مخصصة في Odoo، وليس استبدال قاعدة ركاز.
يشمل المشاريع والعمليات والإنشاءات والمقاولين والجودة والسلامة والمستودعات
والمشتريات والعهد والتعزيز والموارد البشرية والإجازات والرواتب والورشة والأصول
والتدفقات النقدية والقوائم والمتابعات وتعريفات التبويبات.
كلمات المرور وأسرار الإعدادات وحسابات الدخول وسجلات رموز التحقق لا تُصدَّر.

## متطلبات التشغيل

- Python 3.10 أو أحدث؛ لا يحتاج مكتبات إضافية.
- Odoo 18 أو 19 أو 20، وصلاحية External API ضمن خطة تدعمها.
  إصدار 20 يستخدم ir.access لتقييد الشركة ومنح القراءة/الإنشاء/التعديل دون حذف.
  يفحص السكربت أسماء حقول عضوية المجموعات والقوائم قبل إجراء أي كتابة.
- مستخدم تكامل مخول بالشركة المختارة. إعداد النماذج يحتاج صلاحيات إدارة/تخصيص.
- الملفان rekaz_odoo_sync.py وrekaz_to_odoo18.py في نفس مجلد tools.
- تحميل متغيرات tools/odoo_sync.env.example في بيئة العملية بعد ملئها.
  السكربت لا يقرأ .env تلقائيًا. لا ترسل مفتاح API في المحادثة ولا تضعه في كود Studio.
- تحقق من اسم قاعدة Odoo ورقم الشركة واسمها؛ لا نفترض أنها تطابق اسم الموقع.
- Odoo 20 يستخدم JSON-2 ومفتاح API بصفة bearer؛ Odoo 18/19 يبقيان على XML-RPC.
  يتطلب Odoo 20 خطة Custom لواجهة API الخارجية.

## الأوامر من مجلد ركاز

فحص المصدر فقط، بلا اتصال أو كتابة إلى Odoo:

```powershell
python tools/rekaz_odoo_sync.py --sqlite instance/rakaz.db
```

بعد تجهيز بيئة الاختبار ومتغيرات الاتصال، إنشاء النماذج والصلاحيات:

```powershell
python tools/rekaz_odoo_sync.py --setup
```

نسخ البيانات وتحديث ما تغيّر مع رفع الملفات المحلية:

```powershell
python tools/rekaz_odoo_sync.py --apply --uploads webapp/static/uploads
```

استبدل مسار uploads بالمسار الفعلي قبل التطبيق. تشغيل دوري يكون بنفس أمر --apply
عبر مجدول نظام التشغيل؛ لا تضف --setup للتشغيل الدوري. لم يتم تثبيت جدولة تلقائية.
اضبط RAKAZ_DATA_DIR أو --sqlite لتستخدم قاعدة الإنتاج الفعلية لا نسخة قديمة.
حافظ على REKAZ_SOURCE_KEY ثابتًا حتى لا تُنشأ نسخ أخرى من السجلات.
توجد مهلة افتراضية 1.5 ثانية بين طلبات RPC لتقليل خطأ 429 (تجاوز عدد الطلبات).
يمكن رفع ODOO_RPC_INTERVAL إلى 3 ثوانٍ إن استمر الحد. عند 429 أثناء إنشاء
سجل، لا يعيد الكود الكتابة تلقائيًا؛ انتظر دقيقة ثم أعد --apply ليبحث عن السجل
بهوية المصدر أولًا. تظهر رسالة تقدم كل 20 سجلًا، وقد تستغرق أول مزامنة عدة دقائق.

التقرير: outputs/odoo_sync_report.json. رمز الخروج 0 نجاح، 1 خطأ إعداد/اتصال،
2 تعارضات أو روابط/مرفقات تحتاج معالجة. لا ينفذ السكربت إعادة محاولة عمياء بعد
فشل كتابة؛ أعد تشغيله بعد مراجعة السبب، فيبحث عن هوية المصدر قبل الإنشاء.
استخدم عملية واحدة ومكان تشغيل واحد لكل وجهة. القفل محلي؛ لا يمنع عملية على
سيرفر آخر. إذا انقطع التنفيذ وبقي instance/odoo_sync.lock، تحقق من انتهاء
العملية ذات رقم PID داخل الملف قبل حذف القفل.

## تخصيص بنود العقد لمشاريع ركاز في Odoo

يستخدم Odoo الحالي (`reportrek.odoo.com`) إصدار 20.0. افحص الاتصال أولاً؛
الأمر يطلب اسم القاعدة والمستخدم ومفتاح API المخفي، ولا ينشئ نماذج أو ينقل بيانات:

```powershell
python "tools\launch_aamn.py" --check
```

إذا ظهر `http_status=401 reason=authentication_failed`، فالخادم رفض مفتاح API
قبل إجراء أي تغيير. تحقق من اسم قاعدة البيانات `reportrek` واسم دخول المستخدم،
وأن المفتاح جديد/غير منتهي وصادر للحساب نفسه؛ لا تستخدم كلمة المرور بدل المفتاح.
أنشئ مفتاحًا جديدًا عند الحاجة وأدخله محليًا عند الطلب، ولا تحفظه في الملفات أو
ترسله في المحادثة.

بعد نجاح الفحص، يضيف إعداد المخطط حقول تصنيف المعاملة والعقد والبنود وحساب
الإجمالي وقواعد إلزام البنود وزر تقرير الطباعة، دون استيراد السجلات أو ترحيل قيود:

```powershell
python "tools\launch_aamn.py" --boq-setup
```

إذا توقف إعداد سابق بعد إنشاء بعض النماذج أو الحقول، فلا تحذفها يدويًا ولا تبدأ
استيراد البنود. أصلح سبب التوقف ثم أعد `--boq-setup`؛ ينشئ الإعداد العناصر
الناقصة ويحدّث صلاحياته وواجهاته بالمعرّفات نفسها. لا تشغّل `--boq-copy` إلا
بعد انتهاء `--boq-setup` بنجاح.

النطاق محصور بمشروعي «ركاز — المعاملات والأعطال» و«ركاز — معاملات التعزيز /
اسكيمات»؛ يتوقف الإعداد دون كتابة إذا لم يجد الاسمين في الشركة المحددة. يختار
المستخدم «طوارئ» أو «اعتيادي» لكل معاملة. يختار البند من دليل العقد، ويُسحب
سعر الوحدة والكود؛ الإجمالي كمية × السعر، مع زيادة 45% لبنود الطوارئ فقط.
لا يسمح بنقل المعاملة إلى مرحلة لاحقة دون عقد وبند تنفيذ وكمية موجبة. الطباعة
تتضمن كود البند ووصفه والكميات والأسعار والإجمالي.

صفحتا «المستخلص والمالية» و«العقد وبنود الكميات»، وزر طباعة المعاملة، تظهر
ابتداءً من مراحل «الإخلاء المبدئي» و«المستخلص» و«الإخلاء النهائي» فقط. يعتمد
الإظهار على اسم المرحلة ويشمل المشاريع الحالية والمستقبلية التي تستخدم هذه
الأسماء؛ أما إلزام البنود قبل نقل المعاملة فيبقى محصورًا بالمشروعين المحددين أعلاه.

تسمية أرقام المعاملات تشمل جميع معاملات ركاز في جميع المشاريع، ولا تقتصر على
مشروعي BOQ المذكورين أعلاه: يعرض عنوان كل معاملة رقم العطل مع رقم أمر العمل عند
توفره، وإذا لم يوجد رقم عطل يعرض رقم الإشعار مع أمر العمل. يمكن تعديل أرقام
العطل والإشعار وأمر العمل من تبويب «أرقام المعاملة»؛ يُحدّث العنوان فور حفظ
التغيير. يستخرج الإعداد الأرقام الحالية من تفاصيل جميع المعاملات المنقولة،
وتُحفظ الأرقام في حقول مستقلة لدعم تحديثات المعاملات الجديدة أو المعدّلة لاحقًا.

يضيف الإعداد قائمة «بحث معاملات ركاز» ضمن تطبيق المشروع، وتبحث في معاملات
الشركة الحالية بالعنوان أو رقم العطل أو رقم الإشعار أو أمر العمل من حقل بحث
واحد. تظل صلاحيات السجلات محكومة بصلاحيات المشروع الحالية؛ ولا يضيف هذا الإعداد
مستخدمين أو يغيّر مجموعاتهم أو دورة الموافقات.

## ربط حركات المخزون بالمعاملة

الإعداد السابق كان ينشئ مستندات تحويل مسودة للنسخ التاريخية، ولا يحجز مخزونًا
ولا يحدّث الرصيد. خيار `--inventory-copy` معطّل في هذا التشغيل لمنع استيراد
الحركات التاريخية أو تكرارها.

لتفعيل التحويلات الأصلية من داخل سجل المعاملة دون ترحيل حركات قديمة:

```powershell
python "tools\launch_aamn.py" --inventory-setup
```

يتحقق الإعداد من مستودع Odoo «ركاز الانجاز» (المعرّف 1 في قاعدة البيانات
الحالية) ومن مواقع المخزون وأنواع العمليات القياسية. ينشئ موقعًا داخليًا
فارغًا لكل معاملة موجودة في مشروعي ركاز تحت الموقع الأعلى للمستودع مباشرة،
لا تحت `WH/Stock`؛ وبذلك لا تبقى المواد المحولة للمعاملة متاحة للصرف المركزي.
ويضيف آلية لإنشاء الموقع للمعاملات الجديدة. هذه المواقع لا تحمل كمية ابتدائية؛
لا تخلط بين معرّف المستودع والرقم `2` في مسار واجهة المخزون.

يُسجل توريد المورد من شاشة الاستلام القياسية في Odoo إلى `WH/Stock`. المورد الافتراضي
هو «الشركة السعودية للطاقة»، ويمكن اختيار أي مورد آخر مسجل في جهات الاتصال
كمورد. يظهر حقل المورد باسم «استلام من المورد» في نموذج الاستلام. لا تضاف
استلامات المورد ضمن قوائم ركاز الخاصة بحركات المعاملات. أُخفي حقل
«المستند المصدر» من النموذج والقوائم لأن رقم أمر العمل ظاهر؛ لم تُحذف بيانات
المصدر المخزنة من سجلات Odoo.
بعد استلامه والتحقق منه، تنشأ حركة داخلية منفصلة من المخزون المركزي إلى موقع
المعاملة المطلوب. لا تُسجل فاتورة المورد أو الاستلام المركزي كأنها وارد مباشر
للمعاملة.

ينشئ الإعداد في صفحة نظرة عامة على المخزون أربع بطاقات عمليات مخصصة بأسماء
«الوارد»، «المنصرف»، «التالف»، و«المسترجع» دون إعادة تسمية بطاقات Odoo القياسية.
تفتح كل بطاقة قائمة تحويلات Odoo القياسية لنوعها وتسمح بإنشاء التحويل واعتماده
من تطبيق المخزون. عند اختيار المعاملة، يملأ الإعداد تصنيف الحركة وموقعي المصدر
والوجهة المناسبين، ويربط الحركة بالمعاملة وأمر العمل. «الوارد» ينقل من المخزون المركزي إلى موقع المعاملة؛
«المنصرف» يخرج من موقع المعاملة؛ «المسترجع» يعيد إلى المخزون المركزي؛ و«التالف»
يوجه إلى موقع خسائر المخزون.
يبقى استلام المورد القياسي إلى المستودع المركزي كما هو، لكن بطاقته القديمة
تُخفى من لوحة النظرة العامة حسب طلب المستخدم. تُعطّل القوائم الفرعية
المخصصة القديمة، وتُخفى أنواع العمليات المخصصة القديمة من لوحة النظرة العامة
وتُؤرشف حتى لا تبقى ضمن العمليات النشطة. لا تُحذف سجلات التحويل التاريخية
المرتبطة بها. تبقى أنواع العمليات الأساسية التي يعتمد عليها إعداد Odoo القياسي
وتدفقات ركاز الجديدة نشطة، حتى لا تتعطل عمليات المستودع.
يبحث الإعداد عن أسماء أنواع العمليات بلغة الواجهة العربية ثم يضيف معرّفاتها
إلى نطاق لوحة النظرة العامة تراكميًا؛ فلا يعتمد الإخفاء على أسماء مترجمة إلى
الإنجليزية، ولا يستبدل مرشحات موجودة أو يؤثر في أنواع العمليات الأربع.
هذا، مع إزالة مرشحات أسطر الحركة القديمة، يمنع صفحة منفصلة ومرشحات حقول غير
صالحة على `stock.move`. لا تُحذف الحركات السابقة ولا تتغير كمياتها.

يعتمد الإعداد مستودعًا فعّالًا واحدًا فقط للشركة، وهو المستودع المركزي المحدد
بالمعرّف 1. المستودعات المؤرشفة لا تُعد مستودعات تشغيلية ولا تمنع الإعداد.
إذا وجد أكثر من مستودع فعّال، يوقف الإعداد ويعرض المعرّفات والأسماء، ولا ينشئ
مستودعًا أو يؤرشفه أو ينقل مخزونًا تلقائيًا. مواقع المعاملات مواقع داخلية تابعة
للمستودع المركزي وليست مستودعات مستقلة.
تُنشأ مواقع المعاملات مباشرة تحت الموقع الأعلى للمستودع دون مجلد وسيط
`RKAZ-TRANSACTION-MATERIALS`. عند إعادة تشغيل الإعداد، تُنقل المواقع المرتبطة
بالمعاملات من المجلد الوسيط القديم إلى الموقع الأعلى مباشرة، مع الحفاظ على
معرّفات المواقع وكمياتها. لا يحذف الإعداد المجلد القديم ولا ينقل أو يعدل المواقع
الأخرى الموجودة تحته ما لم تكن مرتبطة صراحةً بمعاملة ركاز.
يُسمّى موقع المعاملة برقم العطل، وعند غيابه برقم أمر العمل، وعند غياب الرقمين
باسم المعاملة المسجل في Odoo. يعاد تسمية المواقع الحالية المرتبطة بالمعاملات
وفق هذه القاعدة عند تشغيل إعداد المخزون؛ ولا يُنشأ اسم اصطناعي من معرّف Odoo.

لمراجعة المستودعات الإضافية قبل اتخاذ قرار يدوي، شغّل الفحص للقراءة فقط:

```powershell
python "tools\launch_aamn.py" --inventory-warehouse-audit
```

يعرض الفحص أرصدة الكميات الداخلية والحجوزات وعدد التحويلات المرتبطة بأنواع
عمليات كل مستودع، بما فيها التحويلات الملغاة، كما يعرض مراجع أنواع العمليات
الافتراضية للمستودع (الوارد والمنصرف والداخلي) وحالتها وشركتها. لا يعدل أي بيانات.
إذا توقف إعداد المخزون بسبب نوع عملية غير متوافق، تتضمن رسالة الخطأ معرّف النوع
واسمه وحالته ورمزه والمستودع والشركة لتسهيل التشخيص دون تفعيل النوع تلقائيًا. لا تعتبر
المستودع الإضافي صالحًا للأرشفة تلقائيًا عند خلوه من الرصيد الحالي؛ يجب مراجعة
سجل عملياته وأنواع عملياته أولًا والحصول على موافقة صريحة قبل أرشفته.
إذا كانت أنواع العمليات الافتراضية المرتبطة بالمستودع المركزي مؤرشفة، يتحقق
الإعداد من الشركة والمستودع ورمز كل نوع ويستخدمها كمراجع للمسارات دون إعادة
تفعيلها أو تعديل حالتها؛ تبقى الأنواع الأساسية مؤرشفة.

تظهر في صفحة «مواد المعاملة» أولًا لوحة ملخص موحدة، بصف لكل صنف، وأعمدة الصنف،
والوحدة، والوارد، والمنصرف، والمسترجع، والتالف، ورصيد المعاملة الداخلي، ورصيد
المخزون العام. كميات الوارد والمنصرف والمسترجع والتالف تُحسب من الحركات المعتمدة
فقط، وتُعرض بوحدة الصنف؛ رصيد المعاملة الداخلي هو كمية Odoo الفعلية في موقع
المعاملة، أما رصيد المخزون العام فيُقرأ مباشرة من كميات Odoo في المواقع الداخلية
العامة ضمن المستودع المركزي، باستثناء مواقع المعاملات. لا تُعرض كمية مطلوبة أو
حجز متوقع ضمن الملخص. تُنشأ أسطر الملخص تلقائيًا
للأصناف المرتبطة بحركاتها أو بأرصدتها، ولا تنشئ رصيدًا افتتاحيًا ولا ترحّل حركة.
بعد الملخص تظهر أقسام عرض فقط للحركات الأربع. لا تنشئ الحركة ولا تعدلها صفحة
المعاملة؛ ينفذ أمين المستودع الإدخال أو الإخراج من بطاقات صفحة نظرة عامة على
المخزون ويربط التحويل بالمعاملة هناك. هذا يمنع توجيه أمين المستودع إلى صفحة
مشروع لا تخصه.
تُخفى صفحة «معلومات إضافية» الافتراضية من نموذج المعاملة.

- **الوارد:** تحويل داخلي من `WH/Stock` إلى موقع المعاملة. لا يؤثر
  على الكمية الفعلية إلا عند تأكيد التحويل.
- **المنصرف:** تسليم من موقعها إلى موقع العملاء في Odoo.
- **المسترجع:** تحويل داخلي عكسي إلى `WH/Stock`.
- **التالف:** تحويل مخزني عبر عملية الإتلاف المعدة في Odoo من موقع المعاملة
  إلى موقع خسائر المخزون (Usage: Inventory Loss). لا يُخصم من الرصيد إلا بعد
  اعتماد التحويل، ويُرفض الإعداد إذا لم يجد مسارًا وحيدًا مطابقًا.
- **رصيد المعاملة الداخلي:** يُقرأ من كميات Odoo الفعلية في موقع المعاملة.
- **رصيد المخزون العام:** يُقرأ من كميات Odoo الفعلية للمستودع المركزي، ولا
  يُحسب من أعمدة الحركة ولا يضم مواقع المعاملات.

يُحسب رصيد المعاملة من الحركات المعتمدة: الوارد − المنصرف − المسترجع −
التالف. استخدم «تحقق من التوفر» لحجز الكمية، ولا تعتمد أي تحويل إلا بعد تنفيذ
الحركة الفعلية وبصلاحية مخزون مخوّلة. تبقى الموافقات وصلاحيات
اعتماد الحركات وفق مجموعات Odoo القياسية.

يُفتح نموذج الحركة من المعاملة المطلوبة، ويُثبّت رابط المعاملة بعد اختياره لمنع
تبديله بالخطأ. تبقى المواد قابلة للتغيير، ويمكن اختيار نوع الحركة من الوارد أو
المنصرف أو التالف أو المسترجع وفق صلاحيات المستخدم وضوابط أنواع العمليات في Odoo.

التحويلات القديمة غير المصنفة لا تظهر ضمن بوابات الحركات الأربع ولا تُعتمد
تلقائيًا؛ تبقى سجلاتها كما هي في Odoo للمراجعة عند الحاجة. لترحيل صافي
المواد الحالية في المعاملات إلى مواقعها، بعد إعداد الواجهة ونسخ المعاملات
والمواد إلى Odoo، استخدم لقطة إنتاج معتمدة:

```powershell
python "tools\launch_aamn.py" --inventory-migrate --latest-production
```

أو حدّد ملف SQLite للإنتاج صراحةً باستخدام `--sqlite "المسار\إلى\rakaz.db"`.
لا يستخدم هذا الوضع قاعدة SQLite المحلية الافتراضية. يجمع فقط «منصرف للمعاملة»
كوارد للمعاملة، ويطرح «وارد من موقع العمل» و«إرجاع للمجمعة»؛ أي نوع حركة آخر
مرتبط بمعاملة يُسجل كغير مدعوم في التقرير، ويمنع ترحيل الصنف المتأثر إلى أن
تُراجع دلالته. وينطبق المنع نفسه على الكميات غير الصالحة أو رقم الصنف المفقود.
يطابق الأرقام المرجعية بمعاملة واحدة فقط، ثم يقارن صافي الكمية بموقع
المعاملة ورصيد `WH/Stock`. إذا كان رصيد الصنف المركزي غير كافٍ، ينشئ التحويل
المسودة رغم ذلك ويسجل النقص في التقرير كتنبيه؛ وعند اعتماد التحويل قد يصبح
رصيد `WH/Stock` سالبًا. إذا كان في موقع المعاملة رصيد أعلى من صافي المصدر،
يتوقف عن تعديل الصنف ويسجل تعارضًا للمراجعة.
تُفحص حقول وحدة القياس من مخطط Odoo أولًا، ثم يُبحث بأسماء الوحدات المطلوبة
وتُقرأ السجلات المطابقة منفردةً بالحقول المتاحة فقط. إذا أعاد Odoo خطأ حقل غير
صالح، يوضح سجل التشغيل اسم الحقل دون عرض نص الاستجابة أو بيانات حساسة.

ينشئ الأمر تحويلًا داخليًا **مسودة** لكل معاملة وصنف قابل للترحيل، ولا يعتمد
أي حركة ولا يغيّر الأرصدة الفعلية قبل اعتماد أمين المستودع لها في Odoo.
تظل التحويلات خاضعة لقواعد التحقق المثبتة في Odoo؛ إذا كان امتداد آخر يمنع
الرصيد السالب، يجب تعديل إعداد ذلك الامتداد أو إزالته في Odoo قبل الاعتماد.
إعادة التشغيل لا تنشئ تحويلًا ثانيًا للمعاملة إذا وُجد تحويل سابق بهوية
الترحيل نفسها؛ تُسجل حالته للمراجعة. يُحفظ تقرير المطابقة والنواقص والتعارضات في
`outputs/reportrek_transaction_stock_migration.json`. رمز الخروج 2 يعني وجود
أصناف أو حركات غير مكتملة للمراجعة، حتى لو أُنشئت مسودات لبقية الأصناف.

لم يُنفذ الإعداد على Odoo بمجرد تعديل الشيفرة؛ شغّل الأمر التالي بمفتاح API
محليًا:

```powershell
python "tools\launch_aamn.py" --inventory-setup
```

الإعداد لا يستورد دليل المواد أو يرحّل أي حركات، ولا يغيّر أي أرصدة. يجهز
فقط أسطر الملخص للأصناف التي لها حركة مرتبطة أو رصيد موجود. قبل
الاستخدام، اربط الأصناف يدويًا بأصناف Odoo المخزنية ووحداتها الصحيحة، ثم نفّذ
جردًا فعليًا واعتمد الرصيد الافتتاحي يدويًا من أداة الجرد القياسية في Odoo.
لا تستخدم أرقام الكميات القديمة كرصيد افتتاحي دون مطابقة الجرد.

لاستيراد دليل العقد وبنود المعاملات السابقة من أحدث لقطة إنتاج محمّلة ومتحقق
منها، استخدم الأمر التالي بعد الإعداد. هذا الأمر يكتب بيانات إلى Odoo؛ راجع
التقرير قبل معالجة أي عناصر غير مطابقة:

```powershell
python "tools\launch_aamn.py" --boq-copy --latest-production
```

هذا الأمر يحتاج وجود لقطة إنتاج مكتملة في
`instance\odoo_production_snapshots`؛ لا تستخدم قاعدة SQLite محلية قديمة
كمصدر لأسعار العقد.

## ما الذي ينفذه وما الذي يحتاج ربطًا إضافيًا

- ينشئ سجلًا مخصصًا لكل سجل مصدر، ويحدث السجلات التي تغيّرت، ويربط المفاتيح المعروفة.
- يرصد التعديلات اليدوية على حقول المصدر داخل Odoo ويترك التعارض للمراجعة.
- يمنع نشر جداول غير معروفة حتى تراجع تغطيتها؛ لا يستنتج تلقائيًا أنها آمنة للنشر.
- لا يحذف سجلات Odoo عند حذفها من ركاز؛ تبقى نسخة تاريخية. الحذف المتزامن غير مفعّل.
- ينسخ المرفقات المحلية ضمن المسار المحدد مع فحص المسار والحجم والبصمة.
  مراجع S3/الروابط الخارجية تبقى نصوصًا وتظهر ضمن المرفقات غير المنقولة.
- منح مجموعتي Rekaz Sync يتيح الاطلاع على البيانات المتزامنة بما فيها الرواتب.
  لا تمنحهما لجميع الموظفين. تُمنح مجموعة التعديل لمستخدم تشغيل الإعداد فقط؛
  صلاحيات ركاز الفردية لا تتحول تلقائيًا إلى صلاحيات Odoo.
- السجلات المخصصة ليست فواتير محاسبية مرحّلة أو حركات مخزون أصلية في Odoo.
  لا ترسل هذه الأداة رسائل ولا تنفذ المدفوعات ولا تجعل Odoo مصدر الحسابات.
- النماذج هنا مستقلة عن نموذج reports الظاهر بالصورة. لا تلصق سكربت السيرفر
  في خانة تنفيذ الكود؛ يحتاج Python وقراءة SQLite خارج Odoo.

## كود الصورة: فتح واجهة ركاز من Odoo

انسخ tools/odoo_open_rekaz_action.py.txt إلى «تنفيذ الكود»، وضع رابط ركاز
الفعلي في rekaz_url ثم احفظ وأنشئ إجراء سياقي. هذا يفتح التطبيق الموجود في تبويب
جديد ويحافظ على تسجيل الدخول الحالي لركاز؛ لا يوحّد تسجيل الدخول ولا ينسخ التطبيق.

## التحقق

لفحص هويات المصدر المكررة دون كتابة: `python tools/rekaz_odoo_sync.py --audit-duplicates`.
لمعالجة النسخ المتطابقة دون حذف: `python tools/rekaz_odoo_sync.py --repair-duplicates`.
يُعتمد أقدم سجل، وتُغيّر هوية المصدر واسم النسخ الزائدة مع الاحتفاظ بسجلاتها
ومرفقاتها وروابطها الحالية. تظهر النسخ الزائدة باسم «نسخة مكررة محفوظة»؛ لا تُخفى.
السجلات المعدّلة يدويًا لا تُغيّر. يُحفظ سجل بالقيم السابقة قبل كل كتابة في
outputs/odoo_duplicate_repair_*.json. عند فشل كتابة راجع حالة pending ولا تفترض فشلها.
بعد نجاح المعالجة أعد فحص التكرار قبل --apply. لا تستبدل هويات النسخ المحفوظة يدويًا.

```powershell
python -m unittest discover -s tests -p test_odoo_sync.py
python -m unittest discover -s tests -p test_odoo_migration.py
```

الاختبارات المحلية تستخدم Odoo وهميًا. الاتصال الفعلي وإنشاء النماذج على
wadnooh1.odoo.com لا يمكن تأكيدهما حتى توفير إعدادات الاتصال وخطة API المناسبة.
